# REVIEW.md

List of every defect found in the starter `app/main.py`, along with anything examined and judged fine.

| # | Where (function / line) | What is wrong | How you'd notice it (test, input, or symptom) | How you fixed it |
|---|---|---|---|---|
| 1 | `health()` (line 72-74) | Does not ping MongoDB. Returns 200 even when the database is unreachable, so the readiness probe is useless. | Start the app without MongoDB running; `GET /health` still returns 200 instead of 503. | Added `client.admin.command("ping")` inside a try/except; raise `HTTPException(503, …)` on failure. |
| 2 | `list_employees()` – skip formula (line 93) | `skip = page * page_size` skips one extra page. Page 1 should skip 0 rows, but this skips `page_size` rows. | `GET /employees?page=1&page_size=5` returns the second five employees, not the first five. | Changed to `skip = (page - 1) * page_size`. |
| 3 | `list_employees()` – total count (line 94) | `count_documents({})` ignores the `department` filter so the total is always the collection size. | Filter by `department`; `total` is larger than `len(items)` when it should equal the filtered count. | Changed to `count_documents(q)`. |
| 4 | `list_employees()` – no sort (line 95) | Results are not sorted by `emp_code` ascending as the contract requires. | Records come back in insertion order, not code order. | Added `.sort("emp_code", ASCENDING)`. |
| 5 | `create_employee()` – race condition on duplicate (line 79-80) | Check-then-insert is not atomic. Two simultaneous creates can both pass the `find_one` check and both insert, violating the uniqueness constraint. | Send two concurrent `POST /employees` with the same `emp_code`; may get two 201s. | Removed the pre-check; instead catch `DuplicateKeyError` from the unique index on `emp_code` and return 409. |
| 6 | `create_employee()` – `created_at` is naive (line 82) | `datetime.now()` returns a naive local-time datetime. If the server runs in a non-UTC time zone this stores an incorrect time; PyMongo needs UTC for reliable round-trips. | `created_at` returned in the API will be wrong on a non-UTC server. | Changed to `datetime.now(tz=timezone.utc)`. |
| 7 | `create_employee()` – returns `created_at` as a datetime object (line 85) | The response serialises `created_at` as a datetime string, not epoch milliseconds as the contract requires. | Response contains `"created_at": "2026-01-05T04:30:00"` instead of an integer. | Added `_serialize_employee()` helper that converts `created_at` via `dt_to_ms()`. |
| 8 | `punch_in()` – no 404 on unknown employee (line 100-101) | If `emp` is `None`, the code crashes with `TypeError` when it tries `emp["shift_start"]`, surfacing as a 500. | `POST /attendance/punch-in` with an unknown `emp_code` returns 500 instead of 404. | Added `if not emp: raise HTTPException(404, "employee not found")`. |
| 9 | `punch_in()` – timestamp uses local time (line 102) | `datetime.fromtimestamp(ms / 1000)` returns a naive local-time datetime. Date calculation and storage are then wrong on a non-UTC server. | Punch-in near midnight in IST can produce the wrong attendance date if the server is UTC. | Changed to `ms_to_dt()` which uses `datetime.fromtimestamp(ms // 1000, tz=timezone.utc)`. |
| 10 | `punch_in()` – `punched_at` accepts seconds-level values and floats | No validation: values below `100_000_000_000` (which look like Unix seconds) or floats are silently accepted. Contract says reject with 422. | `POST /attendance/punch-in` with `"punched_at": 1720000000` (seconds) is accepted and stores an absurd 1970s date. | Added `EpochMillis` range validation in the Pydantic model (`field_validator`). |
| 11 | `punch_in()` – race condition on duplicate (line 104-105) | Check-then-insert is not atomic; two simultaneous punch-ins for the same `(emp_code, date)` can both succeed. | Send two concurrent punch-ins; both return 201. | Removed the pre-check; unique compound index `(emp_code, date)` + catch `DuplicateKeyError` → 409. |
| 12 | `compute_late_minutes()` – off-by-one on grace boundary | `minutes > 10` makes 09:40:01 late by `10` but also makes 09:40:00 late (10 > 10 is false, so 09:40:00 correctly gives 0 — but the floor is `int(...)` which truncates, not floors for negative differences). More critically, a punch-in at exactly 09:40:00 should give 0; 09:40:01 should give 10. The condition `minutes > 10` passes the 10-minute mark correctly but the division uses float `/ 60` instead of `// 60`. | `punch_in = 09:40:01, shift 09:30` → `delta = 601s`, `601/60 = 10.016…`, `int(...)=10` ✓ but `punch_in = 09:40:59` → `delta = 659s`, `659/60 = 10.98`, `int(...)=10` ✓. Root issue: the boundary check uses `minutes > 10` where `minutes` is already a float-divided value, not whole seconds. This means `09:40:00 exact` gives `delta=600s`, `600/60=10`, `10 > 10 = False` → 0 ✓, but `09:40:00.900` (which is truncated to `09:40:00` per R1) is fine. The real bug is the function receives an IST datetime but the starter never converts to IST — `datetime.fromtimestamp(ms/1000)` is local time, not IST. | Fixed in conjunction with defect #9: always convert to IST before passing to helper. Replaced float division with integer seconds and `> 600` (strictly more than 10:00 = 600 s). |
| 13 | `compute_overtime()` – ignores overnight shifts | `datetime.fromisoformat(date_str).replace(hour=h, minute=m, tzinfo=IST)` always uses the attendance date. For an overnight shift the shift_end falls the **next** calendar day, so overtime is calculated against the wrong instant, always producing a large negative difference → `max(0, ...)` returns 0. | Employee with shift 22:00-06:00 punches out at 07:00 next day (60 min overtime); overtime is returned as 0. | Detect overnight shift; when overnight, add one day to the base date before building `shift_end` datetime. |
| 14 | `list_attendance()` – loads entire collection into memory (line 144) | `list(db.attendance_logs.find(q))` fetches every matching document before slicing. On 100k records this is slow and memory-heavy. | Response time degrades linearly with collection size. | Use cursor `.sort().skip().limit()` and `count_documents(q)` for the total; never materialize the full result. |
| 15 | `list_attendance()` – returns `_id` as `id` field | The contract defines `AttendanceRecord` with no `id` field. The starter pops `_id` and renames it `id`. | Response contains `"id": "..."` which is not in the schema. | Use `_serialize_record()` which excludes `_id` and never adds an `id` field. |
| 16 | `list_attendance()` – dates not validated; `date_from > date_to` not rejected | No format check or ordering check on the date query params. Contract says 422 if `date_from > date_to`. | `GET /attendance?date_from=2026-12-01&date_to=2026-01-01` returns 200 with an empty result instead of 422. | Added `DATE_RE` format validation and a `date_from > date_to` → 422 check. |

**Things examined and judged not defective:**

- The `compute_work_hours` formula `(punch_out - punch_in).total_seconds() / 3600` is correct in principle; the defect was only in the rounding (Python's built-in `round()` uses banker's rounding, not half-up as R4 requires). I replaced the helper to use `Decimal` with `ROUND_HALF_UP`.
- The IST timezone offset constant `timezone(timedelta(hours=5, minutes=30))` is correct for IST.
- The Pydantic `BaseModel` usage and FastAPI wiring are structurally sound; the defects are in business logic and concurrency handling.
